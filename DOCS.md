# Visual Code

Интерактивный визуализатор выполнения Python-кода для подготовки к ЕГЭ по информатике в рамках проекта **ЕГЭволюция**.

Проект содержит два режима визуализации:

1. **Classic View** — пошаговая анимация с scope-блоками и шариками данных.
2. **Block Scheme** — структурная блок-схема (AST), с динамической пошаговой визуализацией трассировки: подсветка активной строки/блока, токены переменных и вывода, управление воспроизведением.

## Архитектура

```
Python Code
     ↓
  Tracer  (backend/tracer.py — sys.settrace)
     ↓
Execution Steps  (steps[]: line / call / return)
     ↓
  Classic View    (animator.js)
```

```
Браузер                          Бэкенд (Python)
─────────────────────────────    ──────────────────────────
┌─────────────┐   POST /trace    ┌──────────────┐
│  editor.js  │ ─────────────── ▶│  validator   │ ← AST-проверка
│             │                  └──────┬───────┘
│  Пользо-    │   { steps[] }          │ ok
│  ватель     │ ◀─────────────── ┌──────▼───────┐
│  вводит код │                  │   tracer     │ ← sys.settrace
└──────┬──────┘                  └──────────────┘
       │
       ├─ режим Classic ──▶ animator.js
       │
       └─ режим Block Scheme ──▶ block-scheme.js (без запроса к серверу)
```

**Принцип работы:**

1. Пользователь пишет код в редакторе CodeMirror (или выбирает пример из выпадающего списка) и нажимает «Запустить»
2. `api.js` отправляет код на `POST /trace`
3. Бэкенд валидирует код через AST-whitelist
4. `tracer.py` выполняет код с `sys.settrace` и собирает события трёх типов: `call` (вызов функции), `return` (возврат), `line` (шаг строки)
5. Массив шагов (`steps[]`) возвращается в браузер
6. `animator.js` воспроизводит Classic View

## Classic View

Классический пошаговый режим. Запускается автоматически при нажатии «Запустить».

**Что отображается:**

- **Панель кода** — подсветка синтаксиса, активная строка выделена жёлтым фоном.
- **Scope-блоки** — каждый вызов функции получает отдельный блок, переменные обновляются внутри него. Блоки выстраиваются в дерево вызовов.
- **Шарики (DataBall)** — при изменении переменной из текущей строки вылетает цветной шарик и приземляется в нужную ячейку scope-блока.
- **Console** — вывод `print()`, строки появляются по мере выполнения.
- **Управление** — кнопки «⏮ ◀ ▶ ▶▶ ⏭», скорость (Медленно / Нормально / Быстро / Очень быстро), клавиши ← →, Пробел.

**Состояния scope-блока:**

| Класс | Смысл |
|-------|-------|
| `.active` | Выполнение сейчас в этой функции |
| `.waiting` | Вызов сделан, ждёт возврата дочерней функции |
| `.done` | Функция завершена, показывает `ret: значение` |

## Block Scheme

Структурная блок-схема Python-кода, построенная из AST исходного текста. Статика (парсер → layout → SVG) строится **без запроса к серверу**; затем в фоне подгружается трассировка с бэкенда, включающая пошаговую динамику — подсветку, токены, плеер. Активируется кнопкой «Block Scheme» в переключателе режимов перед нажатием «Запустить».

### Архитектура (`block-scheme.js`)

Три независимых слоя:

```
Исходный код (строка)
        ↓
   Layer 1 — Parser       parseCode()
        ↓
   BlockNode[] (дерево)
        ↓
   Layer 2 — Layout       layoutTree()
        ↓
   { lnodes[], edges[] }
        ↓
   Layer 3 — Renderer     renderSVG()
        ↓
   SVG-строка → innerHTML #bs-canvas
```

### Слой 1 — Парсер

`parseCode(src)` разбирает исходный код построчно по отступам (без AST-библиотеки). Возвращает массив узлов `BlockNode`.

**Типы узлов:**

| Тип | Python-конструкция | Форма на схеме |
|---|---|---|
| `assignment` | `x = 5` (литерал справа) | Параллелограмм |
| `action` | `print(x)`, `x = x + 1` | Скруглённый прямоугольник |
| `condition` | `if ... : / else:` | Ромб |
| `loop` | `for i in range(...):` | Шестиугольник |

Узлы `condition` и `loop` содержат вложенные массивы (`yes`, `no`, `body`).

### Слой 2 — Layout Engine

`layoutTree(tree)` рекурсивно обходит дерево и вычисляет `{ cx, cy, w, h }` для каждого блока, а также маршруты стрелок `{ points[], label?, noArrow? }`.

**Ключевые функции:**

| Функция | Назначение |
|---|---|
| `layoutSeq(nodes, cx, y, loopCtx)` | Основной цикл по последовательности. Отслеживает `lastLoop` (exit-стрелка) и `joinY` (join→следующий) |
| `placeLoop(node, cx, topY)` | Размещает шестиугольник + тело. Вычисляет `frameLeft/Right/Top/Bot`. Возвращает `visBot` |
| `layoutCond(node, cx, topY, loopCtx, lnodes, edges, isLastInLoop=true)` | Три режима: top-level, inside-loop-last (back-стрелка), inside-loop-not-last (только join, без back-стрелки) |
| `linSeq(nodes, cx, y, loopCtx, lnodes, edges)` | Укладка последовательности внутри ветви условия. Пробрасывает `loopCtx` во вложенные `layoutCond` с `isLastInLoop=false` |
| `addColArrows(lnodes, edges)` | Постобработка: вертикальные стрелки между соседними блоками в одной колонке |
| `backArrow(fromX, fromY, loopNode)` | Создаёт ленивый объект back-стрелки (без точек). Точки вычисляются в `resolveBackArrows` после того, как у цикла установлен `frameLeft` |
| `nestedLoopBackArrow(innerLoopNode, outerLoopNode)` | Ленивая back-стрелка для случая «вложенный цикл — последний элемент тела родителя». Стартует от хексагона внутреннего цикла (не от последнего действия его тела) — см. [Правило 9](#правило-9) |
| `resolveBackArrows(edges)` | Разворачивает все ленивые back-стрелки (`backArrow` и `nestedLoopBackArrow`) в массивы точек. Вызывается строго до `addColArrows` |

**Три режима `layoutCond`:**

| Режим | Условие | Поведение |
|---|---|---|
| Top-level | `loopCtx == null` | YES/NO уходят горизонтально, широкий bypass для «Нет», merge → joinY |
| Inside-loop, last | `loopCtx != null && isLastInLoop == true` | YES/NO сначала вниз `BACK_DOWN px`, stub для «Нет», joinY → `backArrow()` |
| Inside-loop, not last | `loopCtx != null && isLastInLoop == false` | Те же маршруты, что и last, но без `backArrow()` — возвращает joinY для продолжения тела |

**Маршрутизация стрелок для `if/else` внутри цикла:**

При наличии `else` обе ветви (YES и NO) сходятся в JOIN-точку по центру, из которой идёт **одна** back-стрелка по левой границе рамки (`frameLeft`) к левой точке шестиугольника. Exit-стрелка цикла идёт по правой границе рамки (`frameRight`), что автоматически огибает правую ветвь.

```
      ◇ условие ◇
   Да↙           ↘Нет
 [блок1]       [блок2]
    ↘               ↙
      ──→ join ←──
              ↓ back по frameLeft
 ←─────────────────────────────
 │ ▲ frameLeft              frameRight ▲
 └─────────────────────────────────────┘← рамка
```

### Слой 3 — SVG Renderer

`renderSVG(lnodes, edges)` строит SVG-строку. ViewBox вычисляется автоматически по экстремумам всех координат + отступ `SVG_PAD = 50px`.

**Формы блоков в SVG:**

| Тип | SVG-элемент | Параметры |
|---|---|---|
| `assignment` | `<polygon>` — параллелограмм | `ASSIGN_W=150`, `ASSIGN_H=56`, `skew=22` |
| `action` | `<rect>` — скруглённый | `ACTION_W=140`, `ACTION_H=50`, `rx=10` |
| `condition` | `<polygon>` — ромб | `COND_W=130`, `COND_H=72` |
| `loop` | `<polygon>` — шестиугольник | `LOOP_W=160`, `LOOP_H=62`, `flat=36` |

Стрелки — `<path>` с `marker-end="url(#ar)"` (наконечник) или без (`noArrow: true` у merge-линий).

### Константы (`BS`)

```javascript
const BS = {
  // Размеры блоков
  ASSIGN_W: 150, ASSIGN_H: 56, ASSIGN_SKEW: 22,
  ACTION_W: 140, ACTION_H: 50, ACTION_RX: 10,
  COND_W: 130,   COND_H: 72,
  LOOP_W: 160,   LOOP_H: 62,  LOOP_FLAT: 36,
  TERM_W: 120,   TERM_H: 44,

  // Отступы между блоками
  V_GAP: 56,     H_OFF: 130,
  BACK_PAD: 50,  EXIT_PAD: 50, WRAP_PAD: 90,
  SVG_PAD: 50,

  // Рамки циклов (v2.1.0)
  FRAME_NEST:  35,  // отступ рамки от вложенного цикла с каждой стороны
  FRAME_PAD_X: 25,  // горизонтальный отступ от крайнего узла до рамки
  FRAME_PAD_Y: 10,  // вертикальный отступ сверху/снизу рамки

  // Back-стрелка (v2.1.0)
  BACK_DOWN:   10,  // пикселей вниз перед поворотом влево по рамке
};
```

### Правила маршрутизации стрелок

#### Реализованные правила

**Правило 1 — Рамка цикла (вычисляется, не отображается)**

Каждый узел типа `loop` получает вычисленный прямоугольник: `frameLeft`, `frameRight`, `frameTop`, `frameBot`. Вычисляется снизу вверх в конце `placeLoop`: сначала внутренний цикл, затем внешний расширяется вокруг него (`FRAME_NEST` с каждой стороны) + финальный отступ `FRAME_PAD_X`.

Рамка используется исключительно для маршрутизации стрелок — визуально не отображается (`.bs-loop-frame { display: none }`).

Вложенные рамки строго шире: каждый уровень вложения добавляет 60 px с каждой стороны (`FRAME_NEST × 2`).

---

**Правило 2 — Back-стрелка идёт по левой границе рамки**

Back-стрелка (из конца тела цикла в начало шестиугольника) строится по маршруту:

```
↓ BACK_DOWN px → ← frameLeft → ↑ по frameLeft → → в левую точку шестиугольника
```

Реализовано через ленивые объекты `backArrow(fromX, fromY, loopNode)` — без точек. После того как все циклы вычислили `frameLeft`, вызывается `resolveBackArrows(edges)`, которая достраивает точки, используя актуальное `loopNode.frameLeft`.

При вложении: каждый цикл использует свой `frameLeft` → back-стрелки расходятся по X и не перекрываются.

---

**Правило 3 — Exit-стрелка входит в следующий блок сверху**

Exit-стрелка (из правой точки шестиугольника к следующему блоку после цикла) строится по маршруту:

```
правая точка → frameRight → ↓ до (top−BACK_DOWN) → ← до cx следующего блока → ↓ в верх блока
```

Стрелка всегда входит в блок **сверху** (последний сегмент вертикален). Реализовано в трёх местах: в `layoutTree` (цикл → следующий узел верхнего уровня), в `linSeq` (цикл → следующий узел в ветви условия) и в `placeLoop` (вложенный цикл → следующий узел тела).

При вложении: каждый цикл использует свой `frameRight` → exit-стрелки расходятся по X (для 3 уровней: `475 > 415 > 355`).

Вложенный цикл, являющийся **последним** в теле родителя, не имеет exit-стрелки — его выход идёт через back-стрелку родителя.

---

**Правило 4 — «Нет»-путь if-без-else последним в теле цикла остаётся внутри рамки**

Вместо широкого bypass (`bpX = cx + 208`) используется `stubX = cx + w/2 + 8` — stub-точка прямо у правого кончика ромба. Путь: правый кончик → вниз `BACK_DOWN` → вправо до `stubX` → вниз до joinY → влево к центру. Stub всегда левее `frameRight`.

---

**Правило 5 — Одна back-стрелка на цикл (join-точка)**

Независимо от структуры тела цикла (if-без-else, if/else, elif-цепочка) — всегда создаётся ровно одна back-стрелка. YES и NO ветви сходятся в JOIN-точку по центру, из которой идёт одна `backArrow()`.

---

**Правило 6 — Все стрелки внутри цикла сначала уходят вниз**

Стрелки YES («Да») и NO («Нет») из ромба условия, расположенного внутри цикла, сначала уходят **вниз на `BACK_DOWN = 10 px`** от кончика ромба, и только затем поворачивают в сторону ветви. Это относится ко всем условиям внутри цикла: последнему, не-последнему и вложенным в elif-цепочках.

---

**Правило 7 — Перенос текста не разбивает выражения в скобках**

Функция `splitWords(label)` делит строку на слова по пробелам только на глубине вложенности 0. Пробелы внутри `(...)` и `[...]` не являются точками разбивки: `arr[j + 1]` и `range(n - i - 1)` остаются цельными словами при переносе.

---

**Правило 8 — Не-последнее условие в теле цикла использует ограниченную маршрутизацию**

Условия, за которыми в теле цикла есть ещё элементы, вызываются с `isLastInLoop=false`. Они используют stub-маршрутизацию (правила 4, 6) без создания back-стрелки — функция возвращает joinY, который `placeLoop` использует как `pendingJoinY` для продолжения обхода тела.

Вложенные условия (elif-цепочки) также получают `isLastInLoop=false` через `linSeq`, пробрасывающий `loopCtx` — они никогда не создают back-стрелку самостоятельно.

---

**Правило 9 — Back-стрелка родителя для «вложенный цикл — последний в теле» стартует от хексагона, не от действия** <a name="правило-9"></a>

Когда вложенный цикл является последним элементом тела родителя (`for i: ... for j: ...`, без кода после `for j` внутри `for i`), back-стрелка родителя раньше стартовала от `innerVisBot` — нижней границы всего содержимого внутреннего цикла, т.е. фактически от последнего action-блока его тела. Визуально это выглядело так, будто линия выходит из действия, а не из условия цикла.

Исправлено через `nestedLoopBackArrow(innerLoopNode, outerLoopNode)`: путь стартует от **правого кончика хексагона внутреннего цикла**, обходит его справа по `inner.frameRight` (не задевая саму фигуру), спускается **ниже** точки поворота собственной back-стрелки внутреннего цикла (`inner.frameBot + BACK_DOWN`, чтобы не пересечься с ней), и только потом уходит влево к `outer.frameLeft` и вверх в хексагон родителя.

```
inner.rightTip → inner.frameRight → ↓ (ниже back-стрелки inner) → outer.frameLeft → ↑ → outer-хексагон
```

Корректно компонуется рекурсивно при 3+ уровнях вложенности — каждый уровень использует свои `frameRight`/`frameLeft`, гарантированные Правилом 1 не пересекаться.

### Поддерживаемые конструкции

- Линейная последовательность присваиваний и `print()`
- `if` без `else`, `if / else`, `elif`-цепочки (парсятся как вложенный `if` в `no`-ветви)
- `for` и `while` циклы (оба рисуются шестиугольником)
- Вложенные циклы любой глубины (`for` в `for`, `while` в `for` и т.д.)
- Вложенные условия любой глубины (`if` в `if`)
- Условие или цикл внутри цикла — последний и не последний элемент тела
- Произвольные комбинации вышеперечисленного

### Переключение режимов

В `editor.js` добавлена переменная `vizMode` (`'classic'` / `'blockscheme'`). При нажатии «Запустить»:
- `classic` → запрос к `/trace`, Classic View (`animator.js`)
- `blockscheme` → `startBlockScheme(code)` (локально, без сети) **+** `loadBlockSchemeTrace(code)` (фоновый запрос трассировки, без `await` — статика не ждёт сеть)

Кнопка «← Вернуться к редактору коду» скрывает `#bs-view` и показывает `#input-view`.

### Динамика Block Scheme (v3.0.0)

Поверх статической схемы — пошаговая визуализация трассировки. Реализована полностью внутри `block-scheme.js`, не модифицируя `animator.js`/Classic View; переиспользует только две его чистые функции напрямую: `animateBall()` и `formatValue()`.

#### Подключение трассировки

| Функция | Назначение |
|---|---|
| `loadBlockSchemeTrace(code)` | Фоновый `traceCode()`-запрос. Сохраняет `{steps, error, truncated}` в `bsTrace`. Гонки устаревших ответов отсекаются счётчиком `bsTraceGen` |
| `getBlockSchemeTrace()` | Геттер текущего состояния трассировки |
| `bsShowTraceStatus(message, isError)` / `bsHideTraceStatus()` | Баннер `#bs-trace-warn` — показывает ошибку выполнения/валидации (красный) или предупреждение об усечении на 600 шагах (жёлтый). Переиспользует существующие классы `.error-banner`/`.warn-banner` |

Статика не зависит от результата — если бэкенд недоступен или код не проходит валидатор, диаграмма всё равно строится, а в баннере появляется причина.

#### Номер строки на блоке

Каждый узел (`assignment`/`action`/`condition`/`loop`), кроме терминальных «Начало»/«Конец», получает поле `line` (1-based, при парсинге). В `renderSVG` такой блок оборачивается в `<g data-line="N">` — это и есть хук, на котором держится вся остальная динамика (поиск активного блока, посадка токенов).

#### Код-панель и подсветка

Полностью изолированная от Classic View копия: отдельные DOM id/классы (`#bs-code-display`/`.bs-code-line` против `#code-display`/`.code-line` у Classic), отдельный keydown-листенер в `editor.js`.

| Функция | Назначение |
|---|---|
| `bsBuildCodeDisplay(code)` | Строит `#bs-code-display` с подсветкой синтаксиса (переиспользует `highlightPython()` из `editor.js`) |
| `bsSetActiveLine(lineNum)` | Подсвечивает строку кода |
| `bsSetActiveBlock(lineNum)` | Подсвечивает блок схемы — ищет `[data-line="N"]` в `#bs-svg`, ставит класс `.bs-block-active` |
| `renderBlockSchemeStep(index)` | Снап на шаг `index`: подсветка строки+блока, рендер переменных/консоли, `bsUpdateControls()`. Без анимации — мгновенный переход |

#### Токены переменных и вывода

| Функция | Назначение |
|---|---|
| `bsRenderVars(vars, changedKeys)` | Карточки `.bs-var-card` в `#bs-vars-body`; изменившиеся помечаются `.changed` (пульсация) |
| `bsRenderConsole(output)` | Строки `.bs-console-line` в `#bs-console-body` |
| `bsStepNext(onDone)` | Сравнивает текущий и следующий шаг трассировки. На каждую изменившуюся переменную — синий токен (`animateBall`, `#4F7EF7`) к `#bs-vars-body`; на новый вывод — зелёный (`#059669`) к `#bs-console-body`. После приземления всех токенов коммитит шаг через `renderBlockSchemeStep` |
| `bsAnimating` | Флаг, блокирующий повторный вход в `bsStepNext` пока токен в полёте — защита от гонки при быстрых повторных нажатиях |
| `bsStepPrev()` | Мгновенный снап назад, без анимации (как и в Classic View) |

#### Управление воспроизведением

| Функция | Назначение |
|---|---|
| `bsTogglePlay()` | Запуск/пауза. Если на последнем шаге — перезапускает с начала |
| `bsScheduleNextStep()` | Рекурсивный `setTimeout`-цикл: `bsStepNext(onDone)` → пауза `BS_SPEED_PAUSE[bsSpeed]` → повтор |
| `bsGotoStart()` / `bsGotoEnd()` | Мгновенный прыжок в начало/конец, без анимации |
| `bsSetSpeed(speed)` | Переключает `bsSpeed` (0.5/1/2), визуально — класс `.bs-speed-active` |
| `bsUpdateControls()` | Дизейблит ⏮/◀ на первом шаге, ▶▶/⏭ на последнем, обновляет иконку ▶/⏸ |

`BS_SPEED_PAUSE = { 0.5: 900, 1: 450, 2: 180 }` — пауза между приземлением токена и следующим шагом, мс. На скорости `bsSpeed >= 2` сам перелёт токена тоже ускоряется (`fast=true` в `animateBall`, ~220мс вместо ~450мс) — иначе скорость влияла бы только на паузу, а не на ощущение полёта.

Управление: кнопки `#bs-ctrl-first/prev/play/next/last` + `←`/`→`/`Space` (когда активен `#bs-view`, отдельный листенер в `editor.js`, не пересекается с Classic View).

### `tracer.py` — Трассировщик

Использует `sys.settrace` для перехвата выполнения Python-кода. Генерирует события трёх типов.

**События:**

| Событие | Когда | Ключевые поля |
|---------|-------|---------------|
| `call` | При вызове пользовательской функции | `scope_id`, `parent_id`, `scope_name`, `args`, `depth` |
| `return` | При возврате из функции | `scope_id`, `scope_name`, `return_value`, `depth` |
| `line` | Перед каждой строкой | `scope_id`, `scope_name`, `line`, `variables`, `output` |

**Ключевые особенности:**

- `<module>` frame пропускает события `call`/`return` — только `line`. Это позволяет не создавать scope-блок для глобального уровня через tracer (глобальный блок создаётся отдельно на фронтенде).
- Аргументы функции (`args`) заполняются **на первом `line`-событии** внутри функции, а не на `call` — потому что в Python 3.12 `frame.f_locals` пуст в момент события `call`. Tracer ретроактивно дополняет предыдущий `call`-шаг.
- `scope_id` — уникальный номер каждого вызова функции (инкрементируется с 1). `parent_id` — `scope_id` вызывающей функции (0 = глобальная область).
- `depth` — глубина стека вызовов в момент `call` (0 = вызван из глобального кода).
- Код выполняется в изолированном namespace только с разрешёнными встроенными функциями.
- `print()` перехватывается: вывод копится в `captured_output[]`.
- Лимит: **600 line-шагов**. `call`/`return` в счётчик не входят. При превышении `truncated: true`.
- После `exec()` добавляется синтетический финальный `line`-шаг с итоговым состоянием (если оно отличается от последнего записанного).

**Сериализация значений (`_serialize`):**
- `int`, `float`, `bool`, `None` → как есть
- `str` → обрезается до 200 символов
- `list`, `tuple` → до 30 элементов, рекурсия до глубины 3
- `dict` → до 15 ключей, ключи приводятся к `str`
- `set` → до 15 элементов, сортируется
- Всё остальное → `str(value)[:100]`

## Технические решения

### Почему встроенный HTTP-сервер, а не FastAPI

pip недоступен в среде разработки (SOCKS-прокси блокирует установку пакетов). Бэкенд переписан на `http.server`, `json`, `os` — нулевые зависимости.

### Сдвиг sys.settrace (off-by-one)

`sys.settrace` даёт событие `line` **перед** выполнением строки. Снимок в шаге N содержит переменные, установленные строкой N-1.

Classic View решает это через look-ahead: `scheduleNextStep` сравнивает `steps[N]` и `steps[N+1]`, запускает шарик от текущей строки, а панели обновляет при приземлении шарика.

### Пустые аргументы на call-событии (Python 3.12)

В Python 3.12 `frame.f_locals` возвращает пустой словарь в момент события `call`. Tracer откладывает заполнение `args` до первого `line`-события внутри функции и ретроактивно дополняет предыдущий `call`-шаг.

### Центрированное дерево — почему depth+1

Функции начинаются с `y = (depth+1) * 165 + 16`, то есть со строки 1, а глобальный блок — строка 0. Они никогда не пересекаются по y, функции свободно расходятся влево и вправо.

### Ghost-якорь консоли

Цель шарика для Console (Classic View) — `#console-anchor`, нулевой div в конце `#console-body`. `innerHTML = ''` уничтожает его, поэтому хранится JS-ссылка и все функции очистки восстанавливают его через `consoleBody.appendChild(consoleAnchor)`.

## Roadmap

### Block Scheme — возможные улучшения

**Динамика (обсуждается, не реализовано):**
- Токены, летящие **между блоками схемы** (а не только к панелям «Переменные»/«Вывод») — визуализация потока выполнения вдоль реальной геометрии стрелок (включая изгибы back-стрелок цикла), а не по прямой. Требует: (а) решить, что показывать внутри токена (курсор без значения / чип со значением / гибрид), (б) способ сопоставления перехода шаг→ребро — либо рёбра при построении получают метаданные `fromLine`/`toLine`, либо подбираются геометрически в момент анимации

### v2.2.0

**Block Scheme — полная система маршрутизации (Rules 4–8) + визуальные правки**

Завершена реализация всех правил маршрутизации стрелок. Исправлены ошибки для условий внутри циклов.

**Новые правила маршрутизации:**

- **Правило 4** — «Нет»-путь if-без-else (последнего в теле цикла) использует `stubX = cx + w/2 + 8` вместо широкого `bpX`, остаётся внутри `frameRight`
- **Правило 5** — Одна back-стрелка на цикл: YES и NO ветви сходятся в JOIN-точку, из которой идёт ровно одна `backArrow()`
- **Правило 6** — Все стрелки «Да»/«Нет» из ромба внутри цикла сначала уходят вниз на `BACK_DOWN = 10 px`, затем поворачивают в сторону
- **Правило 7** — `splitWords(label)`: перенос текста учитывает вложенность `[]` и `()`, не разбивает `arr[j + 1]`, `range(n - i - 1)`
- **Правило 8** — Не-последнее условие в теле цикла: `isLastInLoop=false` — ограниченная маршрутизация без back-стрелки, joinY передаётся дальше по телу

**Исправленные ошибки:**

- Не-последнее условие в теле цикла ранее вызывалось с `loopCtx=null` → использовало top-level routing → нарушало R5 (выход за `frameRight`) и R6 (горизонтальный первый сегмент). Исправлено: `placeLoop` теперь передаёт `(ln, ..., false)`.
- Условия внутри elif-цепочек (вложенные через `linSeq`) ранее получали `loopCtx=null` → нарушали R6. Исправлено: `linSeq` принимает и пробрасывает `loopCtx`, всегда передавая `isLastInLoop=false`.

**Визуальные изменения:**

- **Рамки циклов скрыты**: `.bs-loop-frame { display: none }`. Данные рамок (`frameLeft/Right/Top/Bot`) по-прежнему вычисляются для маршрутизации, но прямоугольник не рисуется.
- **Exit-стрелка входит в блок сверху**: добавлена точка поворота `top − BACK_DOWN` перед следующим блоком. Стрелка подходит слева, поворачивает вниз над блоком и входит через верхнюю грань. Исправлено в трёх местах: `layoutTree`, `linSeq`, `placeLoop`.

**Новые сигнатуры:**
- `layoutCond(..., isLastInLoop = true)` — новый 7-й параметр
- `linSeq(nodes, cx, y, loopCtx, lnodes, edges)` — новый 4-й параметр

Classic View не затронут. Бэкенд не изменён.

### v2.1.0

**Block Scheme — правила маршрутизации стрелок (Rules 1–3)**

Исправлены критические ошибки линий для вложенных конструкций (цикл в цикле, условие в цикле). Введена система правил маршрутизации, внедряемых поочерёдно.

**Правило 1 — Рамка цикла:**
- Каждый цикл получает вычисленный `<rect class="bs-loop-frame">` вокруг всего тела
- Вычисление снизу вверх: внутренние рамки известны раньше внешних
- Вложенные рамки автоматически шире: `FRAME_NEST = 35 px` с каждой стороны (итого 60 px разницы на уровень)
- Z-order: рамки → стрелки → блоки

**Правило 2 — Back-стрелка по левой границе рамки:**
- Маршрут: `↓ BACK_DOWN px → ← frameLeft → ↑ → шестиугольник`
- Включает «Правило 8»: 10 px вниз перед поворотом (стрелка выходит из низа блока, не режет его)
- Реализовано через ленивые объекты: `backArrow(fromX, fromY, loopNode)` — точки добавляются в `resolveBackArrows()` после вычисления `frameLeft`
- При вложении 3 уровней back-стрелки располагаются на X: `25, 85, 145` — не пересекаются

**Правило 3 — Exit-стрелка по правой границе рамки:**
- Маршрут: `правая точка → frameRight → ↓ → следующий блок`
- Удалён `exitBendX` — `frameRight` автоматически охватывает все вложенные ветви
- При вложении 3 уровней exit-стрелки: `475 > 415 > 355` — разные X, не пересекаются

**Новые константы BS:** `FRAME_NEST: 35`, `FRAME_PAD_X: 25`, `FRAME_PAD_Y: 10`, `BACK_DOWN: 10`

**Новые функции:** `backArrow()`, `resolveBackArrows()`

**Удалено:** `backPath()`, `exitBendX`

### v2.0.0

**Block Scheme — новый режим визуализации**

Добавлен режим **Block Scheme**: статическая структурная блок-схема, построенная из AST исходного кода без запроса к серверу.

**Новые файлы:**
- `frontend/js/block-scheme.js` (~400 строк) — полный конвейер Parser → Layout → SVG Renderer
- `#bs-view` в `index.html` — новый экран с SVG-канвасом и правой панелью
- `.bs-mode-selector` в `index.html` — переключатель Classic View / Block Scheme
- Стили `.bs-*` в `style.css` — оформление нового режима

**Поддерживаемые конструкции:**
- Линейные последовательности (присваивание, `print`)
- `if` без `else`, `if/else`
- `for` цикл
- `for` + код после (exit-стрелка справа)
- `for` + `if` внутри (back-стрелки из ветвей)
- `for` + `if/else` внутри (join-точка, одна back-стрелка)

**Формы блоков:** параллелограмм (присваивание), скруглённый прямоугольник (действие), ромб (условие), шестиугольник (цикл for).

**Маршрутизация стрелок:**
- Back-стрелка из тела цикла входит в **левую точку** шестиугольника
- Exit-стрелка цикла выходит из **правой точки** шестиугольника к следующему блоку
- При `if/else` внутри цикла обе ветви сходятся в JOIN-точку, из которой идёт одна back-стрелка
- Exit-стрелка автоматически огибает правую ветвь (`exitBendX`)

**Исправленные баги (в процессе разработки):**
1. Ветвь `else` внутри цикла не рисовалась — исправлено
2. Лишняя back-стрелка от промежуточных блоков тела цикла — исправлено
3. Путь «Нет» уходил в цикл вместо блока `else` — исправлено
4. Две раздельные back-стрелки создавали прямоугольную рамку — заменено JOIN-подходом
5. Exit-стрелка проходила сквозь правый ветвь-блок — исправлено через `exitBendX`

Classic View не затронут. Бэкенд не изменён.
